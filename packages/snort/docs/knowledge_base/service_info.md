# Service Info

## Common use cases
The Snort integration for Elastic Agent allows you to ingest, parse, and visualize network intrusion detection and prevention system (IDS/IPS) logs from Snort instances. This provides security teams with deep visibility into network threats and malicious activity.

*   **Intrusion Detection Monitoring:** Real-time monitoring of network traffic against known attack signatures to identify potential breaches, unauthorized access attempts, or policy violations across your infrastructure.
*   **Threat Hunting and Incident Response:** Aggregating Snort alerts into the Elastic Stack enables security analysts to correlate network events with other data sources, such as endpoint logs or cloud audit trails, to investigate complex threats and lateral movement.
*   **Network Compliance Auditing:** Maintaining a centralized repository of Snort logs to meet regulatory requirements (such as PCI-DSS, HIPAA, or SOC2) regarding network security monitoring, integrity checking, and audit logging.
*   **Performance and Tuning:** Analyzing the frequency and types of alerts generated to fine-tune Snort rules. This helps in identifying noisy signatures, reducing false positives, and ensuring that security operations center (SOC) teams are focused on the most critical threats.

## Data types collected
This integration collects the following data streams from Snort deployments:

*   **Snort logs (Logfile):** Collect Snort logs using logfile input. This data stream is designed to monitor local log files generated by the Snort engine. It captures intrusion detection alerts, network metadata (source/destination IPs, ports), and protocol information directly from the file system.
*   **Snort logs (udp):** Collect Snort logs using udp input. This data stream listens for syslog-formatted alerts sent over the network from remote Snort sensors, allowing for centralized collection from multiple appliances without requiring local agent installation on every sensor.

**Supported Log Formats:** 
*   **PFsense CSV:** Structured comma-separated values commonly used in firewall appliances.
*   **Alert Fast:** A single-line summary format for Snort 2.x alerts.
*   **Snort 3 JSON:** Highly structured JavaScript Object Notation logs providing rich event context and easier parsing for Elastic Common Schema (ECS) mapping.

## Compatibility
*   **Snort Versions:** The Snort integration is compatible with **Snort v2.9** and **Snort v3**. While it has been specifically tested against these versions, it is expected to work with other versions that utilize standard output formats like Alert Fast, structured JSON, or standard Syslog.
*   **Elastic Stack:** This integration requires Kibana and Elasticsearch version **^8.11.0** or **^9.0.0**. Ensure your environment meets these version requirements before deployment.

## Scaling and Performance

To ensure optimal performance in high-volume environments, consider the following:
*   **Transport/Collection Considerations:** For environments where data integrity is paramount, use the **logfile** input on the local host where Snort is running to avoid potential packet loss. If using the **udp** input, ensure the network infrastructure between the sensor and the Agent can handle the expected syslog burst rates. UDP is efficient but does not guarantee delivery; for mission-critical security auditing, TCP-based syslog or local logfile collection is preferred.
*   **Data Volume Management:** Snort can generate significant volumes of data depending on the rule set and network traffic. Recommend filtering data at the source by disabling high-volume, low-value rules (e.g., specific ICMP or informational alerts) or adjusting the logging severity levels within the Snort configuration file (`snort.conf` or `snort.lua`) to only forward actionable alerts.
*   **Elastic Agent Scaling:** In high-throughput environments (e.g., 10Gbps+ network segments), deploy multiple Elastic Agents across different network sensors to distribute the ingestion load. For centralized syslog collection via UDP, place Agents behind a network load balancer to distribute traffic evenly and ensure high availability during peak traffic periods.

# Set Up Instructions

## Vendor prerequisites

1. **Administrative Access:** Root or sudo permissions on the Snort host are required to modify configuration files (`snort.conf` or `snort.lua`) and restart the Snort service.
2. **Network Connectivity:** If using the UDP collection method, the Snort host must have network access to the Elastic Agent host on the configured UDP port (default is `9514`).
3. **Snort Installation:** A functional installation of **Snort** v2.9 or **Snort 3** must be present.
4. **Logging Configuration:** Snort must be configured to output alerts in one of the supported formats: **Alert Fast**, **PFsense CSV**, or **Snort 3 JSON**.

## Elastic prerequisites
1.  **Elastic Agent Enrollment:** The Elastic Agent must be installed and enrolled in a Fleet policy.
2.  **Healthy Status:** Ensure the Agent status is **Healthy** in the Kibana Fleet management UI.
3.  **Connectivity:** Ensure the Agent has a clear network path to the Elasticsearch and Fleet Server endpoints.
4.  **Version Requirement:** Verify that your Kibana and Elasticsearch version is at least **8.11.0**.

## Vendor set up steps

### For Syslog (UDP) Collection (Recommended for Snort 2.x):
1.  **Locate Configuration:** Open your Snort configuration file, typically located at `/etc/snort/snort.conf` or `/usr/local/etc/snort/snort.conf`.
2.  **Enable Syslog Output:** Search for the output section (Section 6) and add or uncomment the following line to direct alerts to the Elastic Agent:
    ```
    output alert_syslog: host=<agent-ip>:9514, LOG_AUTH LOG_ALERT
    ```
    *Replace `<agent-ip>` with the actual IP address of the host running the Elastic Agent.*
3.  **Verify Port:** Ensure the port specified (`9514`) matches what you will configure in the Kibana integration settings.
4.  **Save and Exit:** Save the changes to the `snort.conf` file.
5.  **Restart Snort:** Apply the changes by restarting the Snort service:
    ```bash
    sudo systemctl restart snort
    ```

### For Logfile Collection (Snort 2.x Alert Fast):
1.  **Configure Fast Logging:** Edit your `snort.conf` file to enable the fast alert output.
2.  **Define Output Path:** Add the following line to ensure alerts are written to a specific file:
    ```
    output alert_fast: /var/log/snort/fast_alerts.log
    ```
3.  **Save and Restart:** Save the configuration and restart the Snort process to begin writing to the new log file.
4.  **Set Permissions:** Ensure the log file is readable by the agent: `sudo chmod 644 /var/log/snort/fast_alerts.log`.

### For Logfile Collection (Snort 3 JSON):
1.  **Locate Lua Config:** Open your `snort.lua` configuration file.
2.  **Configure JSON Logger:** Locate the `alert_json` block and enable file output:
    ```lua
    alert_json = { file = true }
    ```
3.  **Define Outputs:** Ensure the `alert_json` logger is included in the outputs section of your `ips` block configuration:
    ```lua
    ips = { outputs = { { alert_json = alert_json } } }
    ```
4.  **Restart Snort:** Save the Lua file and restart Snort 3 to begin generating structured JSON logs.

## Kibana set up steps

### Collecting logs from Snort instances (input: logfile)
1.  In Kibana, navigate to **Integrations > Snort**.
2.  Click **Add Snort**.
3.  Under the **Snort logs** policy template, find the section for **Collect Snort logs (input: logfile)**.
4.  Configure the following variables:
    *   **Paths** (`paths`): The list of paths to your Snort log files. Default: `/var/log/snort/alert.log`.
    *   **Multi-line Alert Full logs** (`multiline_full`): Enables multiline support if reading the Snort Alert Full log format. Default: `False`.
    *   **Internal Networks** (`internal_networks`): The internal IP subnet(s) of the network. Default: `private`.
    *   **Timezone Offset** (`tz_offset`): By default, datetimes in the logs will be interpreted as relative to the timezone configured in the host where the agent is running. If ingesting logs from a host on a different timezone, use this field to set the timezone offset (e.g., `Europe/Amsterdam`, `EST`, or `-05:00`) so that datetimes are correctly parsed. Default: `local`.
    *   **Preserve original event** (`preserve_original_event`): Preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.
5.  Save the integration to apply the policy to your Elastic Agent.

### Collecting logs from Snort instances (input: udp)
1.  In Kibana, navigate to **Integrations > Snort**.
2.  Click **Add Snort**.
3.  Under the **Snort logs** policy template, find the section for **Collect Snort logs (input: udp)**.
4.  Configure the following variables:
    *   **Syslog Host** (`syslog_host`): The interface address the agent should listen on for incoming UDP traffic. Default: `localhost`.
    *   **Syslog Port** (`syslog_port`): The UDP port the agent listens on for Snort syslog data. Default: `9514`.
    *   **Internal Networks** (`internal_networks`): The internal IP subnet(s) of the network. Default: `private`.
    *   **Timezone Offset** (`tz_offset`): By default, datetimes in the logs will be interpreted as relative to the timezone configured in the host where the agent is running. If ingesting logs from a host on a different timezone, use this field to set the timezone offset so that datetimes are correctly parsed. Default: `local`.
    *   **Preserve original event** (`preserve_original_event`): Preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.
5.  Ensure the **Syslog Port** (default `9514`) is open on the host's firewall to allow incoming traffic from the Snort sensor.
6.  Save the integration to your Agent policy.

# Validation Steps

After configuration is complete, verify that data is flowing correctly.

### 1. Trigger Data Flow on Snort:
- **Trigger a test alert:** From a remote machine, run a simple port scan against the Snort sensor using Nmap: `nmap -sS <snort_ip>`. This should trigger default "GPL SCAN" or similar rules.
- **Use Curl to trigger web rules:** If you have web-related rules enabled, run `curl http://<snort_ip>/?cmd=cat%20/etc/passwd` to trigger directory traversal signatures.
- **Verify local log writing:** Run `tail -f /var/log/snort/alert.log` (or your configured path) to ensure Snort is actively writing alerts to the local disk.

### 2. Check Data in Kibana:
1. Navigate to **Analytics > Discover**.
2. Select the `logs-*` data view.
3. Enter the KQL filter: `data_stream.dataset : "snort.log"`
4. Verify logs appear. Expand a log entry and confirm these fields:
   - `event.dataset` (should be `snort.log`)
   - `source.ip` and/or `destination.ip`
   - `event.action` or `event.outcome`
   - `message` (the raw Snort alert text)
5. Navigate to **Analytics > Dashboards** and search for "Snort" to view pre-built visualizations.

# Troubleshooting

## Common Configuration Issues

- **Network Connectivity/Firewalls**: If using UDP and logs aren't appearing, verify that no local firewall (like `iptables` or `ufw`) is blocking traffic on the configured port (e.g., `9514`). Use `tcpdump -i any udp port 9514` on the Agent host to confirm packets are arriving.
- **Incorrect File Paths**: For the Logfile input, ensure the **Paths** variable in Kibana exactly matches the location where Snort is writing logs. Snort 3 often appends timestamps or specific names to logs if not explicitly named.
- **Permission Denied**: The Elastic Agent user must have read access to the Snort log directory. You may need to add the `elastic-agent` user to the `snort` group or adjust directory permissions: `chmod 755 /var/log/snort`.
- **Port Conflicts**: Ensure no other service is already listening on the UDP port assigned to the Snort integration. Use `ss -lnup | grep <port>` to check for conflicts.

## Ingestion Errors

- **Format Mismatch**: If logs appear in Kibana but are not parsed correctly (resulting in `tags: ["_grokparsefailure"]`), ensure Snort is outputting in one of the supported formats (Fast, CSV, or Snort 3 JSON). The integration will not parse custom formats or "Full" output without additional configuration.
- **Timezone Discrepancies**: If alerts appear with the wrong timestamp, check the **Timezone Offset** (`tz_offset`) setting in the integration configuration. Snort logs often lack timezone metadata, leading the Agent to assume the local host's time.
- **Identifying Failures**: Look for the `error.message` or `event.ingested` fields in Discover. If the `message` field contains the raw log but other fields like `source.ip` are missing, the parser is failing to match the log format.
