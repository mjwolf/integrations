# Service Info

WatchGuard Firebox is a powerful network security appliance designed to control and monitor all traffic between internal trusted networks and external networks. Running on the Fireware OS, these devices provide comprehensive security features including firewalling, VPN, and threat prevention. This integration allows administrators to ingest Firebox logs into the Elastic Stack for centralized visibility, long-term retention, and security analysis.

## Common use cases

- **Security Monitoring and Threat Detection:** Monitor firewall logs for blocked connections, intrusion prevention system (IPS) alerts, and malware detections to identify potential security threats in real-time.
- **Network Traffic Analysis:** Analyze traffic patterns and bandwidth usage to optimize network performance and identify unauthorized applications or high-usage users.
- **Regulatory Compliance and Auditing:** Maintain long-term storage of system events, configuration changes, and administrative access logs to meet compliance requirements such as PCI-DSS, HIPAA, or GDPR.
- **Operational Troubleshooting:** Use diagnostic and event logs to identify hardware issues, interface status changes, or VPN connectivity problems across the Firebox environment.

## Data types collected

This integration collects logs from WatchGuard Firebox appliances using the following data stream:

- **WatchGuard Firebox logs (log):** Collecting logs via syslog over UDP. This stream collects all messages generated by the Firebox appliance. Data includes:
    * **Firewall Logs:** Detailed records of allowed and denied traffic based on configured policies, including source and destination information.
    * **Security Alarms:** High-priority notifications regarding detected threats, intrusion attempts, and system-level alerts.
    * **Authentication Logs:** Events related to user login attempts, administrative access, and VPN authentication sessions.
    * **Diagnostic and Performance Data:** Information regarding system health, CPU/memory usage, and interface status.

All collected messages are parsed into Elastic Common Schema (ECS) fields for consistent analysis across the Elastic Stack.

## Compatibility

- **Elastic Requirements:** This integration requires Kibana version **8.13.0** or newer.
- **Vendor Requirements:** This integration has been specifically tested and validated against **WatchGuard Firebox** appliances running **Fireware v12.10.3**. It is generally compatible with other versions of Fireware that support standard syslog output.

## Scaling and Performance

To ensure optimal performance in high-volume environments, consider the following:

- **Transport/Collection Considerations:** This integration utilizes Syslog over UDP for data ingestion. While UDP offers high-speed transport with low overhead, it does not guarantee delivery. Ensure the network path between the Firebox and the Elastic Agent is stable and has sufficient bandwidth to prevent packet loss during traffic bursts. In high-latency environments, consider placing the Elastic Agent geographically close to the Firebox appliance to minimize transit time.
- **Data Volume Management:** Configure the Firebox appliance to forward only necessary events. Use the Firebox's internal logging filters to exclude high-frequency, low-value events (such as specific performance or diagnostic logs) to reduce the indexing load on your Elastic cluster. Limiting logging to only "Denied" traffic for high-volume policies or specific severity levels can also significantly reduce data ingest rates.
- **Elastic Agent Scaling:** For high-throughput environments or deployments with multiple Firebox appliances, deploy multiple Elastic Agents behind a network load balancer to distribute the UDP syslog traffic evenly. Ensure the host machines have sufficient CPU resources to handle the regex-heavy parsing required for syslog messages. For extremely large environments, dedicate specific Agent policies to network logging to isolate performance.

# Set Up Instructions

## Vendor prerequisites

- **Administrative Access:** You must have administrative credentials for the Fireware Web UI or Policy Manager to modify logging settings.
- **Network Connectivity:** The Firebox must be able to reach the Elastic Agent host over the network. By default, this integration uses UDP port `9528`, which must be open on any intermediary firewalls.
- **Firmware Requirement:** Ensure the device is running Fireware v12.10.3 or later for full compatibility with the tested log formats.
- **Logging Enabled:** Individual policies on the Firebox (e.g., Packet Filter or Proxy policies) must have "Send a log message" enabled for their specific traffic to be forwarded.

## Elastic prerequisites

- **Elastic Agent:** The Elastic Agent must be installed on a host and successfully enrolled in Fleet.
- **Kibana Version:** A minimum version of **8.13.0** or later is required to support this integration package.
- **Network Path:** Ensure the host running the Elastic Agent is configured to allow inbound UDP traffic on the port specified in the integration settings (default is `9528`).

## Vendor set up steps

### For Syslog over UDP Collection:
1. Log in to your WatchGuard Firebox using the **Fireware Web UI**.
2. From the left navigation pane, select **System**, and then click **Logging**.
3. Select the **Syslog Server** tab to configure remote logging destinations.
4. Check the box for **Send log messages to these syslog servers**.
5. Click **Add** to open the Syslog Server configuration dialog box.
6. In the **IP Address** field, enter the IP address of the host where your Elastic Agent is installed.
7. In the **Port** field, enter the port number configured in the Elastic integration (default is `9528`).
8. From the **Log Format** drop-down list, select **Syslog**.
9. In the **Log Message Content** section, ensure both **The time stamp** and **The serial number of the device** checkboxes are selected to ensure proper event identification and timing.
10. In the **Syslog Settings** section, assign syslog facilities for each message type. It is recommended to use the default Local facilities (Local0 through Local4).
11. Click **Save** to apply the configuration. 
12. Navigate to your firewall policies and ensure the **Log this message** option is enabled on the specific policies you wish to monitor.

## Kibana set up steps

### Collecting logs from WatchGuard Firebox via UDP input.

1. In Kibana, navigate to **Management > Integrations**.
2. Search for **WatchGuard Firebox** and select it.
3. Click **Add WatchGuard Firebox**.
4. Configure the following input variables:
   - **Listen Address** (`listen_address`): The bind address to listen for udp connections. Set to `0.0.0.0` to bind to all available interfaces. Default: `localhost`.
   - **Listen Port** (`listen_port`): The UDP port number to listen on. Default: `9528`.
   - **Timezone Offset** (`tz_offset`): When interpreting syslog timestamps without a time zone, use this timezone offset. Default: `UTC`. Both a canonical ID (such as "Europe/Amsterdam") and an HH:mm differential (such as "-05:00") are acceptable formats.
   - **Preserve original event** (`preserve_original_event`): Preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.
5. Under **Existing hosts**, select the Agent policy where you want to deploy this integration.
6. Click **Save and continue**, then **Roll out changes** to deploy the configuration to your Elastic Agents.

# Validation Steps

After configuration is complete, verify that data is flowing correctly.

### 1. Trigger Data Flow on WatchGuard Firebox:
- **Authentication event:** Log out and log back into the Fireware Web UI to generate administrative access logs.
- **Interface event:** If safe to do so, perform a brief administrative status change on a test interface (e.g., toggle an interface description).
- **Web traffic:** Browse several websites from a workstation behind the Firebox. Ensure the firewall policies for that workstation have "Send a log message" enabled.
- **Diagnostic logs:** Navigate to **Diagnostics > Maintenance** and perform a "Ping" or "DNS Lookup" to generate diagnostic activity.

### 2. Check Data in Kibana:
1. Navigate to **Analytics > Discover**.
2. Select the `logs-*` data view.
3. Enter the KQL filter: `data_stream.dataset : "watchguard_firebox.log"`
4. Verify logs appear. Expand a log entry and confirm these fields:
   - `event.dataset` (should be `watchguard_firebox.log`)
   - `source.ip` and/or `destination.ip`
   - `event.action` (e.g., "allow" or "deny")
   - `observer.serial_number` (matches the Firebox serial)
   - `message` (the raw syslog payload)
5. Navigate to **Analytics > Dashboards** and search for "WatchGuard Firebox" to confirm visualizations are populating.

# Troubleshooting

## Common Configuration Issues

- **Port Mismatch**: The Firebox defaults to port 514 for syslog, while the Elastic integration defaults to 9528. Ensure both the Firebox destination port and the Elastic Agent "Listen Port" are identical.
- **Firewall Obstruction**: If the Elastic Agent is running on a Linux host, the local firewall (e.g., `iptables` or `ufw`) may block incoming UDP packets on port 9528. Use `tcpdump -i any udp port 9528` on the Agent host to verify if packets are arriving.
- **Binding Address**: If the "Listen Address" is set to `localhost`, the Agent will only accept logs from its own host. Change this to `0.0.0.0` to accept logs from external Firebox appliances.
- **Missing Timestamp/Serial**: If fields are not parsing correctly, ensure that "The time stamp" and "The serial number of the device" were both checked in the Firebox Syslog Server settings.

## Ingestion Errors

- **Parsing Failures**: If logs appear in Kibana but contain the tag `_grokparsefailure`, verify that the **Time stamp** and **Serial number** options are enabled in the Firebox syslog settings. The integration's grok patterns expect these fields to be present.
- **Timezone Mismatches**: If logs appear to be delayed or from the future, check the **Timezone Offset** setting in the Kibana integration configuration. This should match the timezone configured on the Firebox appliance.
- **Incomplete Fields**: Check the `error.message` field in Discover. This field often contains specific information about which part of the syslog header or message body failed to map to ECS.
