# Service Info

## Common use cases

The Trend Micro Deep Security integration provides comprehensive visibility into the security posture of physical, virtual, and cloud-based server environments. By ingesting logs into the Elastic Stack, security teams can centralize their monitoring and response workflows.
- **Threat Detection and Response:** Monitor real-time security events from protection modules such as Anti-Malware, Intrusion Prevention, and Web Reputation to identify and mitigate active threats.
- **Compliance Auditing:** Retain and analyze administrator activity and system events to meet regulatory requirements (e.g., PCI-DSS, HIPAA) by tracking who accessed the system and what changes were made.
- **Security Posture Monitoring:** Track the health and status of Deep Security Agents across the infrastructure, ensuring that protection policies are correctly applied and that agents are communicating with the manager.
- **Centralized Log Management:** Aggregating Deep Security logs with other infrastructure data in Kibana allows for cross-source correlation, enabling faster root-cause analysis during security incidents.

## Data types collected

This integration collects logs from Trend Micro Deep Security using three primary input methods. Each method populates the `deep_security` data stream:

- **Trend Micro Deep Security logs (`deep_security`):** This data stream collects comprehensive system, security, and administrator events.
    - **Collect Trend Micro Deep Security logs via TCP input:** Collect Trend Micro Deep Security logs via TCP input. This method is used when the vendor is configured to forward logs over a reliable TCP connection.
    - **Collect Trend Micro Deep Security logs via UDP input:** Collect Trend Micro Deep Security logs via UDP input. This method is used when the vendor is configured to forward logs over UDP for lower network overhead.
    - **Collect Trend Micro Deep Security logs via Filestream input:** Collect Trend Micro Deep Security logs via Filestream input. This method collects logs by reading directly from local log files on the host where Trend Micro components are installed.

Captured data categories include:
- **System Events:** Logs generated by the Deep Security Manager, including administrator logins, management console actions, and software updates.
- **Security Events:** Detailed logs from protection modules, including Anti-Malware (detections and scans), Firewall (rule triggers), Intrusion Prevention (exploit attempts), Integrity Monitoring (file changes), and Log Inspection.
- **Data Formats:** Logs are typically received in Syslog format, often encapsulated in Common Event Format (CEF) for standardized parsing into Elastic Common Schema (ECS) fields.

## Compatibility

This integration is specifically designed for and tested against **Trend Micro Deep Security 20**. It is compatible with environments running Deep Security 20 on-premise or in cloud deployments.
- **Elastic Requirements:** Requires Kibana version `^8.13.0` or `^9.0.0`.
- **Licensing:** For users with a Trend Micro Vision One XDR license, it is recommended to use the dedicated Trend Micro Vision One integration for enhanced cross-layered detection capabilities.

## Scaling and Performance

To ensure optimal performance in high-volume environments, consider the following:

- **Transport/Collection Considerations:** When collecting logs over the network, choosing the correct protocol is essential. **TCP** is recommended for reliability as it ensures delivery through acknowledgement, which is critical for security auditing. **UDP** offers lower overhead and higher throughput but may result in data loss during network congestion. Note that individual Deep Security Agents typically forward logs directly via UDP, whereas the Deep Security Manager can be configured for either.
- **Data Volume Management:** To manage high volumes of log data, it is recommended to filter events at the source within the Trend Micro Deep Security Manager. Configure the vendor appliance to forward only necessary events (e.g., prioritizing Intrusion Prevention and Anti-Malware) and specific severity levels to avoid saturating the Elastic Agent and network bandwidth.
- **Elastic Agent Scaling:** For high-throughput environments receiving logs from thousands of Deep Security agents, a single Elastic Agent may become a bottleneck. Deploy multiple Elastic Agents behind a network load balancer to distribute incoming Syslog traffic evenly. Place Agents close to the data source to minimize latency and ensure the ingestion pipeline remains performant and resilient.

# Set Up Instructions

## Vendor prerequisites

1. **Administrative Access:** You must have an account with administrative privileges in the Trend Micro Deep Security Manager console.
2. **Network Connectivity:** Ensure that the Deep Security Manager can communicate with the Elastic Agent over the configured port (default is `9510`).
3. **Format Requirements:** The Deep Security environment must be configured to export logs in **CEF** (Common Event Format) to ensure high-fidelity parsing by the Elastic integration.
4. **Local Firewall:** Firewalls on the Elastic Agent host must allow incoming traffic on the specified protocol (**TCP** or **UDP**) and port (e.g., `9510`).

## Elastic prerequisites

- **Elastic Agent:** The Elastic Agent must be installed and enrolled in Fleet.
- **Kibana Version:** This integration requires Kibana version **8.13.0** or **9.0.0** and higher.
- **Connectivity:** Ensure the Elastic Agent is configured to listen on a network interface accessible to the Trend Micro components. Setting the **Listen Address** to `0.0.0.0` is common for multi-homed hosts.

## Vendor set up steps

### For Syslog (TCP/UDP) Collection:

1. Log in to your **Trend Micro Deep Security Manager** console.
2. Navigate to **Policies > Common Objects > Other > Syslog Configurations**.
3. Click **New > New Configuration** to create a new syslog destination.
4. On the **General** tab, provide the following details:
   - **Name**: Enter a descriptive name, such as `Elastic-Agent-Syslog`.
   - **Server Name**: Enter the IP address or hostname of the Elastic Agent.
   - **Server Port**: Enter the port number configured in the Elastic Agent (default is `9510`).
   - **Transport**: Select **UDP** (standard for direct agent forwarding) or **TCP** (standard for Manager-based forwarding).
   - **Event Format**: Select **CEF** (Common Event Format) for optimal parsing.
   - **Facility**: Select a syslog facility, such as `LOCAL0`.
5. Under **Agents should forward logs**, select **Via the Deep Security Manager (indirectly)** if you want centralized management, or **Directly to the Syslog server** if you want individual agents to send logs.
6. Click **Apply** and then use the **Test Connection** button to verify the DSM can reach the Elastic Agent.

### Forwarding System and Security Events:

1. To forward **System Events**: Navigate to **Administration > System Settings > Event Forwarding**. In the "Forward System Events to a remote computer" section, select the `Elastic-Agent-Syslog` configuration. Click **Save**.
2. To forward **Security Events**: Navigate to the **Policies** tab and double-click the policy you wish to update.
3. Go to **Settings > Event Forwarding**.
4. For each module (Anti-Malware, Intrusion Prevention, etc.), select your `Elastic-Agent-Syslog` configuration from the dropdown.
5. Click **Save** to apply the policy changes.

### For Logfile Collection:

1. Ensure the Deep Security Manager or Agent is configured to write logs to a local disk file.
2. Identify the absolute path to the log files (e.g., `/var/log/ds_agent.log` or a custom path defined in the DSM).
3. Ensure the user account running the Elastic Agent has read permissions for these log files and the directories containing them.

## Kibana set up steps

1. In Kibana, navigate to **Management** > **Integrations**.
2. Search for and select **Trend Micro Deep Security**.
3. Click **Add Trend Micro Deep Security**.
4. Follow the prompts to add the integration to an existing Elastic Agent policy or create a new one.
5. Configure the inputs based on your collection method:

### Collecting logs from Trend Micro Deep Security via TCP.
*   **Listen Address** (`listen_address`): The bind address to listen for TCP connections. Default: `localhost`. Set to `0.0.0.0` to bind to all available interfaces.
*   **Listen Port** (`listen_port`): The TCP port number to listen on. Default: `9510`.
*   **Timezone Offset** (`tz_offset`): When interpreting syslog timestamps without a time zone, use this timezone offset. Datetimes recorded in logs are by default interpreted in relation to the timezone set up on the host where the agent is operating. Both a canonical ID (such as `Europe/Amsterdam`) and an HH:mm differential (such as `-05:00`) are acceptable.
*   **Preserve original event** (`preserve_original_event`): If enabled, preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.

### Collecting logs from Trend Micro Deep Security via UDP.
*   **Listen Address** (`listen_address`): The bind address to listen for UDP connections. Default: `localhost`. Set to `0.0.0.0` to bind to all available interfaces.
*   **Listen Port** (`listen_port`): The UDP port number to listen on. Default: `9510`.
*   **Timezone Offset** (`tz_offset`): When interpreting syslog timestamps without a time zone, use this timezone offset. Datetimes recorded in logs are by default interpreted in relation to the timezone set up on the host where the agent is operating. Both a canonical ID (such as `Europe/Amsterdam`) and an HH:mm differential (such as `-05:00`) are acceptable.
*   **Preserve original event** (`preserve_original_event`): If enabled, preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.

### Collecting logs from Trend Micro Deep Security via File.
*   **Paths** (`paths`): A list of glob-based paths that will be crawled and fetched. Example: `/var/log/trendmicro/*.log`.
*   **Timezone Offset** (`tz_offset`): When interpreting syslog timestamps without a time zone, use this timezone offset. Datetimes recorded in logs are by default interpreted in relation to the timezone set up on the host where the agent is operating. Both a canonical ID (such as `Europe/Amsterdam`) and an HH:mm differential (such as `-05:00`) are acceptable.
*   **Preserve original event** (`preserve_original_event`): If enabled, preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.

6. Click **Save and continue** to deploy the configuration to the Elastic Agent.

# Validation Steps

After configuration is complete, verify that data is flowing correctly.

### 1. Trigger Data Flow on Trend Micro Deep Security:
- **Authentication event:** Log out of the Deep Security Manager and log back in to generate a "User Signed In" system event.
- **Configuration event:** Navigate to a policy and temporarily toggle a setting, such as changing a log inspection rule status, then click **Save**.
- **Test Syslog Connection:** Use the **Test Connection** button within the **Syslog Configurations** menu in Deep Security Manager to send a test packet to the Elastic Agent host.

### 2. Check Data in Kibana:
1. Navigate to **Analytics > Discover**.
2. Select the `logs-*` data view.
3. Enter the KQL filter: `data_stream.dataset : "trendmicro.deep_security"`
4. Verify logs appear in the results. Expand a log entry and confirm the presence of these fields:
   - `event.dataset` (should be `trendmicro.deep_security`)
   - `source.ip` (the IP of the Deep Security Manager or Agent)
   - `event.action` or `event.outcome`
   - `message` (the raw log payload)
5. Navigate to **Analytics > Dashboards** and search for "Trend Micro Deep Security" to verify data visualization.

# Troubleshooting

## Common Configuration Issues

- **Port Conflict**: If the Elastic Agent fails to start the input, check if another process is already using port `9510`. Use `netstat -ano | grep 9510` (Linux) or `Get-NetTCPConnection -LocalPort 9510` (Windows).
- **Listen Address Bind Failure**: If the Elastic Agent is set to `localhost`, it will not receive traffic from external Deep Security components. Change the **Listen Address** to `0.0.0.0` in Kibana.
- **Policy Not Applied**: Security events will not flow until the Syslog configuration is explicitly assigned within a Policy. Verify that the correct policy is applied and saved.
- **Firewall Blocking**: Ensure host-based firewalls (like iptables or Windows Firewall) and network firewalls allow traffic on the designated TCP/UDP port.

## Ingestion Errors

- **Parsing Failures**: If logs appear in Kibana but are not properly parsed into fields, check the `error.message` field. This often happens if the **Event Format** in Deep Security is not set to **CEF**.
- **Timezone Mismatch**: If events appear to be delayed or from the future, ensure the `tz_offset` variable in the Kibana configuration matches the timezone of the Deep Security Manager.
- **Truncated Logs**: Syslog over UDP has a maximum packet size. If logs are very large and getting cut off, consider switching the transport to TCP if supported by your configuration.
