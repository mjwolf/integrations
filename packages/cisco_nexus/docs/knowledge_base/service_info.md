# Service Info

The Cisco Nexus integration allows for the comprehensive monitoring of system messages, errors, and operational logs generated by Cisco Nexus data center switches. By ingesting these logs into the Elastic Stack, administrators gain deep visibility into network fabric stability, hardware health, and configuration changes, enabling proactive troubleshooting and enhanced security auditing across the data center environment.

## Common use cases

- **Network Security Auditing:** Track user logins, logout events, and configuration changes within the NX-OS environment to detect unauthorized access or accidental configuration drift.
- **Hardware and Interface Troubleshooting:** Monitor system errors related to line cards, power supplies, and fan modules, as well as interface state changes (up/down events) to minimize downtime.
- **Performance and Capacity Planning:** Analyze system messages related to resource exhaustion, such as TCAM limits or high CPU/memory utilization, to inform infrastructure scaling decisions.
- **Centralized Log Management:** Aggregating logs from multiple Nexus 9000, 3172T, and 3048 series switches into a single searchable interface for faster cross-device correlation and root cause analysis.

## Data types collected

This integration collects the following data streams:

- **Cisco Nexus logs (logs):** Captures system messages and error logs generated by the NX-OS operating system.
    - **Collect Cisco Nexus logs via TCP input:** Collect Cisco Nexus logs via TCP input. This ensures reliable delivery of system messages by using the Transmission Control Protocol.
    - **Collect Cisco Nexus logs via UDP input:** Collect Cisco Nexus logs via UDP input. This is suitable for high-volume environments where low overhead is prioritized over guaranteed delivery.
    - **Collect Cisco Nexus logs via Filestream input:** Collect Cisco Nexus logs via Filestream input. This collects logs directly from local log files stored on the device or a management host, useful for offline analysis.
- **Data Formats:** The integration specifically parses Cisco NX-OS formatted syslog messages, including details like timestamps, severity levels, facility codes, and mnemonics.
- **Content:** Logs include system alerts, critical errors, debugging information, and informational messages regarding the switch fabric and operating system state.

## Compatibility

The Cisco Nexus integration is compatible with the following product versions:
- **Cisco Nexus Series:** Specifically tested against **9000 Series**, **3172T**, and **3048** switches running NX-OS.
- **Kibana Requirements:** This integration requires **Kibana version ^8.11.0** or **^9.0.0** for full functionality and dashboard compatibility.
- **Elastic Subscription:** This integration is available with a **Basic** subscription.

## Scaling and Performance

To ensure optimal performance in high-volume data center environments, consider the following:

- **Transport/Collection Considerations:** Users can choose between TCP and UDP for network-based log collection. **TCP** is recommended for environments where log integrity and delivery confirmation are critical, though it may introduce slight overhead. **UDP** (default port `9506`) is preferred for high-throughput network environments where the loss of an occasional log entry is acceptable to maintain maximum switch performance.
- **Data Volume Management:** To manage the volume of data sent to the Elastic Stack, administrators should configure the `severity-level` on the Cisco Nexus CLI. By limiting forwarded logs to level 6 (informational) or level 5 (notifications) and above, you can significantly reduce the ingest volume and storage requirements while still capturing important operational events. Avoid debug-level logging in production unless troubleshooting a specific issue.
- **Elastic Agent Scaling:** For high-density environments with hundreds of Nexus switches, deploy multiple Elastic Agents behind a network load balancer to distribute the syslog traffic evenly. Ensure the host systems running the Agent have sufficient CPU and memory to handle the aggregate throughput from high-volume 10/40/100 Gigabit switches. Place Agents as close to the data sources as possible to reduce network latency.

# Set Up Instructions

## Vendor prerequisites

1. **Administrative Access:** You must have `network-admin` or `vdc-admin` privileges to access the Cisco Nexus CLI and modify global configuration settings.
2. **Network Connectivity:** Ensure the switch has a clear network path to the Elastic Agent host. The appropriate ports (default `9506` for TCP/UDP) must be open on any intermediary firewalls.
3. **Management VRF Knowledge:** Identify the correct Virtual Routing and Forwarding (VRF) instance (usually `management`) to ensure syslog traffic is routed correctly to the Elastic Agent.
4. **NX-OS Version:** Ensure the switch is running a supported version of NX-OS consistent with the 9000, 3172, or 3048 series requirements.

## Elastic prerequisites

1. **Elastic Agent Installation:** The Elastic Agent must be installed on a host reachable by the Cisco Nexus switches.
2. **Agent Enrollment:** The Agent must be enrolled in Fleet and have a policy assigned that includes the Cisco Nexus integration.
3. **Kibana Version:** Ensure your Elastic Stack is running version **8.11.0** or later.

## Vendor set up steps

### For Syslog (TCP/UDP) Collection:

1. **Enter Global Configuration Mode**:
   Access the Cisco Nexus CLI and enter configuration mode:
   ```bash
   switch# configure terminal
   ```

2. **Configure the Syslog Server**:
   Define the Elastic Agent as a logging target. Replace `<agent-ip-address>` with the IP of your Agent and `<severity-level>` with your desired level (e.g., 6 for informational).
   ```bash
   switch(config)# logging server <agent-ip-address> <severity-level>
   ```

3. **Configure Source Interface**:
   Specify a consistent source for log packets (e.g., `mgmt0` or `loopback0`):
   ```bash
   switch(config)# logging source-interface <interface>
   ```

4. **Specify the Management VRF**:
   If the Agent is reachable via the management network, append the VRF configuration:
   ```bash
   switch(config)# logging server <agent-ip-address> <severity-level> use-vrf management
   ```

5. **Enable High-Precision Timestamps**:
   Ensure millisecond precision for accurate correlation in Kibana:
   ```bash
   switch(config)# logging timestamp milliseconds
   ```

6. **Save Configuration**:
   Persist changes to the startup configuration:
   ```bash
   switch# copy running-config startup-config
   ```

### For Logfile Collection:

1. **Enable Local File Logging**:
   Configure the switch to store system messages in a local file buffer:
   ```bash
   switch(config)# logging logfile <filename> <severity-level> [size <bytes>]
   ```
   Example: `logging logfile NexusLogs 6 size 4096000`

2. **Verify File Creation**:
   Ensure the log file is being populated correctly:
   ```bash
   switch# show logging last 20
   ```

3. **Elastic Agent Access**:
   Ensure the Elastic Agent has read permissions for the directory where the Nexus log files are stored if the Agent is running on a management host with access to the switch filesystem.

## Kibana set up steps

### Collecting logs from Cisco Nexus via TCP.
1. In Kibana, navigate to **Integrations** > **Cisco Nexus**.
2. Click **Add Cisco Nexus**.
3. Select the input **Collecting logs from Cisco Nexus via TCP**.
4. Configure the following variables:
   - **Listen Address** (`listen_address`): The bind address to listen for TCP connections. Set to `0.0.0.0` to bind to all available interfaces. Default: `localhost`.
   - **Listen Port** (`listen_port`): The TCP port number to listen on. Default: `9506`.
   - **Timezone Map** (`tz_map`): A collection of timezones found in Cisco Nexus logs (as defined in each `tz_short`), and the replacement value (as defined in each `tz_long`) which should be the full proper IANA Timezone format.
   - **Timezone Offset** (`tz_offset`): When interpreting syslog timestamps without a time zone, use this timezone offset (e.g., "Europe/Amsterdam" or "-05:00").
   - **Preserve original event** (`preserve_original_event`): Preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.
5. Save the integration to deploy the configuration to your Elastic Agents.

### Collecting logs from Cisco Nexus via UDP.
1. In Kibana, navigate to **Integrations** > **Cisco Nexus**.
2. Click **Add Cisco Nexus**.
3. Select the input **Collecting logs from Cisco Nexus via UDP**.
4. Configure the following variables:
   - **Listen Address** (`listen_address`): The bind address to listen for UDP connections. Set to `0.0.0.0` to bind to all available interfaces. Default: `localhost`.
   - **Listen Port** (`listen_port`): The UDP port number to listen on. Default: `9506`.
   - **Timezone Map** (`tz_map`): A collection of timezones found in Cisco Nexus logs (as defined in each `tz_short`), and the replacement value (as defined in each `tz_long`) which should be the full proper IANA Timezone format.
   - **Timezone Offset** (`tz_offset`): When interpreting syslog timestamps without a time zone, use this timezone offset (e.g., "Europe/Amsterdam" or "-05:00").
   - **Preserve original event** (`preserve_original_event`): Preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.
5. Save the integration to deploy the configuration.

### Collecting logs from Cisco Nexus via file.
1. In Kibana, navigate to **Integrations** > **Cisco Nexus**.
2. Click **Add Cisco Nexus**.
3. Select the input **Collecting logs from Cisco Nexus via Filestream**.
4. Configure the following variables:
   - **Paths** (`paths`): A list of glob-based paths that will be crawled and fetched.
   - **Timezone Map** (`tz_map`): A collection of timezones found in Cisco Nexus logs and their IANA replacements.
   - **Timezone Offset** (`tz_offset`): When interpreting syslog timestamps without a time zone, use this timezone offset.
   - **Preserve original event** (`preserve_original_event`): Preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.
5. Save the integration to deploy the configuration.

# Validation Steps

After configuration is complete, verify that data is flowing correctly.

### 1. Trigger Data Flow on Cisco Nexus:
- **Configuration change:** Enter and exit global configuration mode: `configure terminal` then `exit`
- **Interface event:** Toggle a test interface: `shutdown` then `no shutdown` on an unused port
- **Authentication event:** Log out and log back into the administration interface
- **Verify status:** Execute `show logging server` on the switch to confirm the message count to the Agent IP is increasing

### 2. Check Data in Kibana:
1. Navigate to **Analytics > Discover**.
2. Select the `logs-*` data view.
3. Enter the KQL filter: `data_stream.dataset : "cisco_nexus.log"`
4. Verify logs appear. Expand a log entry and confirm these fields:
   - `event.dataset` (should be `cisco_nexus.log`)
   - `source.ip` and/or `observer.ip`
   - `event.action` or `event.outcome`
   - `message` (the raw log payload)
5. Navigate to **Analytics > Dashboards** and search for "Cisco Nexus" to view the pre-built dashboards.

# Troubleshooting

## Common Configuration Issues

- **Port Binding Conflicts**: If the Elastic Agent fails to start the listener, ensure the configured **Listen Port** (default 9506) is not being used by another process and that the **Listen Address** is set to `0.0.0.0` if the Agent needs to listen on all interfaces.
- **Unreachable Syslog Server**: Ensure the `use-vrf management` command is used if the Elastic Agent is located in a network reachable only through the management interface. Verify connectivity using `ping <agent-ip> vrf management` from the switch.
- **Timestamp Mismatches**: If logs appear with incorrect times in Kibana, ensure `logging timestamp milliseconds` is enabled on the switch and that the **Timezone Offset** or **Timezone Map** is correctly configured in the integration settings to match the switch's local time settings.
- **Dropped UDP Packets**: If logs are missing during high-traffic periods, check for interface drops on the switch or the Agent host. Consider switching to the TCP input for more reliable transport.

## Ingestion Errors

- **Parsing Failures**: If the `error.message` field indicates parsing issues, verify that the Cisco Nexus model is one of the tested series (9000, 3172T, 3048). Differences in NX-OS versions may occasionally result in slight log format variations.
- **Missing Original Event**: If you are unable to see the raw log string for debugging, ensure that **Preserve original event** is checked in the Kibana configuration.
- **Empty Field Mappings**: Check the `event.original` field in Discover to ensure the log message follows the standard Cisco NX-OS format. If the format is non-standard, fields like `cisco_nexus.mnemonic` may not populate correctly.
