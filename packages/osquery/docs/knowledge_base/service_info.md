# Service Info

## Common use cases
The OSQuery integration is designed to provide deep visibility into endpoint activity by collecting and decoding JSON-formatted result logs generated by the `osqueryd` daemon.
- **Endpoint Threat Hunting:** Use SQL-like queries to monitor system state, such as running processes, open network connections, and loaded kernel modules, to identify indicators of compromise (IoCs) across your fleet.
- **Compliance and Auditing:** Track changes to critical system files, user accounts, and configuration settings to ensure systems remain in compliance with internal security policies or regulatory standards like PCI-DSS or HIPAA.
- **Hardware and Software Inventory:** Automatically maintain an up-to-date inventory of hardware specifications, installed software packages, and browser extensions across Linux, macOS, and Windows environments.
- **Operational Monitoring:** Monitor system performance and resource utilization by scheduling recurring queries that capture the state of system services and resource-intensive background tasks.

## Data types collected

This integration collects data from the local filesystem where osquery writes its query execution results.

Based on the Data Stream Summaries, this integration includes:
- **Osquery result logs (log):** Collect Osquery result logs using log input. This datastream (dataset: `osquery.result`) captures the output of scheduled queries as defined in the osquery configuration, providing a detailed record of system changes and states over time.

Additionally, the logs adhere to the following characteristics:
- **Data Formats:** Logs are expected in JSON format, which is the standard output for the filesystem logging driver in osquery.
- **Specific File Paths:** 
    - Linux/macOS: `/var/log/osquery/osqueryd.results.log*`
    - Windows: `C:\Program Files\osquery\log\osqueryd.results.log*`

## Compatibility
The **Osquery** integration was officially tested against version **2.10.2**, though it is highly likely to be compatible with version **2.10.2 and newer** (including the latest 5.x releases) due to the stability of the osquery JSON log format. This integration is supported on **Linux**, **macOS**, and **Windows** operating systems where the Elastic Agent is deployed.

This integration requires **Kibana version 8.11.0 or newer**.

## Scaling and Performance

To ensure optimal performance in high-volume environments, consider the following:
- **Transport/Collection Considerations:** This integration utilizes the `logfile` input to read data from the local filesystem. To prevent data loss, ensure that osquery's log rotation is configured to retain files long enough for the Elastic Agent to process them. Large result sets from complex queries can increase disk I/O; therefore, queries should be optimized to return only necessary fields.
- **Data Volume Management:** Manage data volume by selecting specific osquery "packs" or optimizing the `interval` of scheduled queries. Use differential logging (the default) instead of snapshot logging to significantly reduce volume by only recording changes in system state. For high-volume environments, avoid running high-frequency queries on tables with high churn, such as `processes` or `socket_events`, without proper filtering.
- **Elastic Agent Scaling:** While a single Elastic Agent can handle typical osquery log volumes for most endpoints, high-load servers monitoring frequent events (like process execution audits) may require additional resources. Ensure the host has sufficient CPU and memory allocated for the Agent. In extremely high-throughput scenarios, consider increasing the Agent's internal queue size to handle spikes in log generation.

# Set Up Instructions

## Vendor prerequisites

1. **Administrative Access:** You must have root or sudo permissions on Linux/macOS, or Administrator privileges on Windows, to install osquery and configure the flagfiles.
2. **osqueryd Installation:** The `osqueryd` daemon must be installed and running on the target host.
3. **Filesystem Logger Plugin:** The `filesystem` logging driver must be configured (this is the default setting for osquery).
4. **UTC Timestamps:** Ensure that the osquery configuration is set to use UTC timestamps to maintain consistency across different time zones.
5. **Log Format:** Osquery must be configured to write results in JSON format (default behavior for the filesystem logger).

## Elastic prerequisites

1. **Elastic Stack Version:** Ensure your Kibana and Elasticsearch instances are running version **8.11.0** or higher.
2. **Elastic Agent Enrollment:** Elastic Agent must be installed on the host and enrolled in a policy via Fleet.
3. **Network Connectivity:** The host must have network connectivity to the Elastic Stack (Elasticsearch and Kibana) to ship logs and receive configuration updates.
4. **Permissions:** The Elastic Agent must have read permissions for the directories and files where osquery writes its logs (e.g., `/var/log/osquery/`).

## Vendor set up steps

### For Logfile Collection:
1.  **Locate the osqueryd Configuration File:**
    Identify the configuration path for your operating system:
    *   **Linux:** `/etc/osquery/osquery.conf`
    *   **macOS:** `/var/osquery/osquery.conf`
    *   **Windows:** `C:\Program Files\osquery\osquery.conf`

2.  **Configure the Filesystem Logging Driver:**
    Open the `osquery.conf` file in a text editor with administrative privileges. Ensure the `options` section contains the following settings to enable the `filesystem` driver and UTC timestamps:
    ```json
    {
      "options": {
        "logger_plugin": "filesystem",
        "logger_path": "/var/log/osquery/osqueryd.results.log",
        "logger_utc": true,
        "disable_logging": false
      }
    }
    ```
    *Note: On Windows, use `C:\\Program Files\\osquery\\log\\osqueryd.results.log` (with escaped backslashes) for the `logger_path`.*

3.  **Define Scheduled Queries:**
    In the same `osquery.conf` file, ensure you have a `schedule` section defined with at least one query to generate logs. For example:
    ```json
    "schedule": {
      "system_info": {
        "query": "SELECT * FROM system_info;",
        "interval": 3600
      }
    }
    ```

4.  **Restart the osqueryd Service:**
    Apply the configuration changes by restarting the service:
    *   **Linux:** `sudo systemctl restart osqueryd`
    *   **macOS:** `sudo launchctl stop com.facebook.osqueryd && sudo launchctl start com.facebook.osqueryd`
    *   **Windows:** Run `Restart-Service -Name osqueryd` in an elevated PowerShell prompt.

5.  **Verify Log File Creation:**
    Check the file system to ensure the result log file has been created and contains JSON data. On Linux, use `tail -f /var/log/osquery/osqueryd.results.log`.

## Kibana set up steps

### Collecting result logs from Osquery instances (input: logfile)

1. In Kibana, navigate to **Management > Integrations**.
2. Search for and select **osquery**.
3. Click **Add Osquery Logs**.
4. Configure the following variables for the `logfile` input:
   - **Paths** (`paths`): Enter the list of paths to the Osquery result logs. You can use patterns with wildcards to include rotated logs. 
     - Default: `['/var/log/osquery/osqueryd.results.log*']`
   - **Preserve original event** (`preserve_original_event`): Check this box to preserve a raw copy of the original event, which will be added to the field `event.original`.
     - Default: `False`
5. Click **Save and continue** to add the integration to an Elastic Agent policy.
6. Deploy the policy to the hosts running `osqueryd`.

# Validation Steps

After configuration is complete, verify that data is flowing correctly.

### 1. Trigger Data Flow on Osquery:
- **Modify query interval:** Temporarily change a scheduled query interval in `osquery.conf` to a low value (e.g., `10` seconds) and restart the service to force immediate log generation.
- **Perform a system change:** If monitoring the `users` table, create a temporary local user account to trigger a differential log entry.
- **Check log growth:** Confirm the file at `/var/log/osquery/osqueryd.results.log` (or Windows equivalent) is increasing in size as queries execute.

### 2. Check Data in Kibana:
1. Navigate to **Analytics > Discover**.
2. Select the `logs-*` data view.
3. Enter the KQL filter: `data_stream.dataset : "osquery.result"`
4. Verify logs appear. Expand a log entry and confirm these fields:
   - `event.dataset` (should be `osquery.result`)
   - `event.action` (often maps to the osquery `action` field like `added` or `removed`)
   - `osquery.result.name` (the name of the query)
   - `message` (the raw JSON log payload)
5. Navigate to **Analytics > Dashboards** and search for "OSQuery".

# Troubleshooting

## Common Configuration Issues
- **Missing UTC Timestamps**: If the timestamps in Kibana appear offset or incorrect, ensure `"logger_utc": true` is explicitly set in the `osquery.conf` options section.
- **Permission Denied**: On Linux, the Elastic Agent must have read permissions for the `/var/log/osquery/` directory and the `osqueryd.results.log` file. If the Agent is running as a non-root user, adjust the directory permissions or add the user to the `osquery` group.
- **Incorrect Logger Plugin**: Ensure the `logger_plugin` is set to `filesystem`. If set to `syslog` or `tls`, osquery will not write logs to the local file path that the Elastic Agent is monitoring.
- **Log Path Mismatch**: Verify that the path defined in `logger_path` in `osquery.conf` matches exactly with the **Paths** variable configured in the Kibana integration settings.

## Ingestion Errors

- **JSON Parsing Failures**: Ensure that the logger plugin is set to `filesystem` and not `syslog` or another plugin that might wrap the JSON in extra headers. The integration expects a clean JSON object per line.
- **Incomplete Events**: If `preserve_original_event` is disabled and fields are missing, check the `error.message` field in Kibana. This often contains details about mapping conflicts or parsing errors.
- **Field Mapping Conflicts**: If osquery returns a custom column name that conflicts with an existing Elastic Common Schema (ECS) field, the data may be moved to `labels` or cause a mapping error. Check the `error.type` field for mapping exceptions.
