# Service Info

The Suricata integration for Elastic enables the seamless collection and analysis of logs from the Suricata high-performance Network Intrusion Detection and Prevention System (IDS/IPS). By ingesting Suricata’s Extensible Event Format (EVE) JSON logs, this integration provides security teams with deep visibility into network traffic, protocol transactions, and potential security breaches directly within the Elastic Stack.

## Common use cases
The Suricata integration for Elastic provides a comprehensive solution for ingesting and analyzing network security events from one of the industry's most powerful open-source IDS/IPS engines.
- **Intrusion Detection and Prevention:** Monitor real-time security alerts generated by Suricata's signature-based engine to detect and respond to malicious network activity such as malware C2, exploits, and scans.
- **Network Traffic Analysis (NTA):** Leverage detailed protocol logs (HTTP, DNS, TLS) to visualize traffic patterns, identify unusual spikes in volume, or investigate the source and destination of specific network flows.
- **Threat Hunting:** Proactively search through enriched network session data and transaction logs to identify Indicators of Compromise (IoCs) that may not have triggered a traditional signature alert.
- **Security Auditing and Compliance:** Maintain a long-term, searchable record of network transactions and security events required for regulatory compliance and post-incident forensic investigations.

## Data types collected

This integration collects several categories of network telemetry via the following data streams:

- **Suricata eve logs:** Collect Suricata eve logs using log input. This stream ingests the primary EVE JSON output which includes:
    - **Alerts:** Logs generated when network traffic matches specific security rules.
    - **Protocol Metadata:** Detailed transaction logs for protocols including DNS, HTTP, TLS, SSH, SMTP, and SMB.
    - **Flow Records:** Summaries of network connections, including byte counts, packet counts, and connection duration.
    - **Anomalies:** Events indicating protocol violations or suspicious packet structures.
    - **Stats:** Periodic performance metrics regarding Suricata's packet processing and engine health.

## Compatibility

This integration is compatible with **Suricata** versions **5.x, 6.x, and 7.x** that support the Extensible Event Format (EVE) JSON output.

It requires the **Elastic Stack** version **8.11.0 or higher** (as specified in the integration manifest) to ensure compatibility with the ingestion pipelines and pre-built dashboards.

## Scaling and Performance

To ensure optimal performance in high-volume environments, consider the following:
- **Transport/Collection Considerations:** This integration utilizes the `logfile` input to monitor the `eve.json` file. Ensure the local disk subsystem has sufficient IOPS to handle simultaneous writes from Suricata and reads from the Elastic Agent. For extremely high-volume environments, consider using a dedicated high-speed SSD for the log directory to minimize latency and prevent disk I/O bottlenecks.
- **Data Volume Management:** Suricata can generate significant amounts of data. Use the `suricata.yaml` configuration to selectively enable only high-value event types. For instance, while `alert` and `dns` are critical for security, `flow` logs generate the highest volume and should be enabled only if required for specific auditing or NTA needs. Reducing the number of enabled event types directly reduces the CPU and storage requirements on the Elastic Stack.
- **Elastic Agent Scaling:** Deploy a dedicated Elastic Agent on the host running Suricata to ensure it has adequate CPU and memory resources to process the EVE JSON logs without impacting Suricata's packet capture performance. In multi-sensor environments, use Fleet to manage consistent policies across all distributed Suricata nodes and monitor the Agent's resource consumption to ensure it keeps up with the log generation rate.

# Set Up Instructions

## Vendor prerequisites
- **Administrative Access:** Root or sudo-level permissions on the host running Suricata to modify configuration files and restart services.
- **Suricata Installation:** A functional installation of Suricata (v5.0+) configured to monitor network interfaces.
- **File System Permissions:** The user account running the Elastic Agent must have read access to the Suricata log directory (typically `/var/log/suricata/`) and the `eve.json` file.
- **EVE JSON Support:** Suricata must be compiled with JSON support (standard in most modern distributions via `libjansson`).
- **Disk Space:** Adequate disk space to store local EVE JSON logs before they are ingested by the Elastic Agent.

## Elastic prerequisites

- **Elastic Agent Installation:** An Elastic Agent must be installed on the Suricata host or a centralized log-collection host that has access to the Suricata log files.
- **Fleet Enrollment:** The Elastic Agent must be enrolled in Fleet and assigned to a valid agent policy.
- **Version Requirements:** Ensure the Elastic Stack and Elastic Agent are version **8.11.0** or higher.
- **Connectivity:** The host running the Elastic Agent must have network connectivity to the Elastic Stack (Elasticsearch and Fleet Server).

## Vendor set up steps

### For Logfile Collection:

1.  **Open the Configuration File:** Access the primary Suricata configuration file, usually located at `/etc/suricata/suricata.yaml`, using a text editor with administrative privileges.
    ```bash
    sudo vi /etc/suricata/suricata.yaml
    ```
2.  **Locate the Outputs Section:** Find the `outputs:` header in the YAML configuration.
3.  **Configure EVE-LOG:** Ensure the `- eve-log:` section is configured correctly. Set `enabled: yes` and `filetype: regular`.
    ```yaml
    outputs:
      - eve-log:
          enabled: yes
          filetype: regular
          filename: eve.json
    ```
4.  **Select Log Types:** Within the `eve-log` section, define which `types` to collect. It is recommended to at least include `alert`, `anomaly`, `dns`, and `http`.
    ```yaml
    types:
      - alert
      - anomaly
      - dns
      - http:
          extended: yes
      - tls:
          extended: yes
      - flow
    ```
5.  **Verify Directory Permissions:** Ensure the directory `/var/log/suricata/` allows the Elastic Agent to access files.
    ```bash
    sudo chmod 755 /var/log/suricata/
    sudo chmod 644 /var/log/suricata/eve.json
    ```
6.  **Restart Suricata:** Apply the changes by restarting the Suricata service.
    ```bash
    sudo systemctl restart suricata
    ```

## Kibana set up steps

### Collecting eve logs from Suricata instances (input: logfile)

1. In Kibana, navigate to **Management > Integrations** and search for **Suricata**.
2. Click **Add Suricata**.
3. Follow the prompts to add the integration to an existing Elastic Agent policy or create a new one.
4. Configure the following variables for the **Suricata logs** input:
   - **Paths** (`paths`): List of absolute paths to the Suricata EVE JSON log files. Default: `['/var/log/suricata/eve.json']`.
   - **Preserve original event** (`preserve_original_event`): Preserves a raw copy of the original event, added to the field `event.original`. Default: `False`.
5. Under **Advanced options**, you may configure additional settings such as custom tags or processors if needed.
6. Click **Save and continue** and then **Save and deploy changes**.

# Validation Steps

After configuration is complete, verify that data is flowing correctly.

### 1. Trigger Data Flow on Suricata:
- **Generate Test Alert:** Execute a command that triggers a standard IDS signature. Use `curl` to visit a known test domain: `curl http://testmyids.com`.
- **Generate DNS Traffic:** Perform a DNS lookup to generate a DNS event: `nslookup elastic.co`.
- **Generate HTTP/TLS Traffic:** Browse a website via the command line to generate transaction logs: `curl -L https://www.google.com`.
- **Check File Growth:** Confirm that `/var/log/suricata/eve.json` is increasing in size after these actions.

### 2. Check Data in Kibana:
1. Navigate to **Analytics > Discover**.
2. Select the `logs-*` data view.
3. Enter the KQL filter: `data_stream.dataset : "suricata.eve"`
4. Verify logs appear. Expand a log entry and confirm these fields:
   - `event.dataset` (should be `suricata.eve`)
   - `source.ip` and/or `destination.ip`
   - `event.action` or `event.outcome`
   - `message` (the raw log payload)
5. Navigate to **Analytics > Dashboards** and search for "Suricata" to open the **[Logs Suricata] Overview** dashboard and verify visualizations are populating.

# Troubleshooting

## Common Configuration Issues

- **Service Status**: If no data is appearing, first verify the Suricata service is active. Run `sudo systemctl status suricata`. If the service is failed, check the Suricata logs for syntax errors in `suricata.yaml`.
- **Output Disabled**: Ensure that `enabled: yes` is explicitly set under the `eve-log` section in the configuration. If set to `no`, Suricata will not write the JSON file that the Agent is monitoring.
- **Incorrect File Path**: Verify that the path provided in the Kibana integration settings exactly matches the `filename` and default log directory (usually `/var/log/suricata/`) specified in the vendor configuration.
- **Permission Denied**: The Elastic Agent often runs as a specific user (e.g., `root` or `elastic-agent`). Ensure this user has read access to `eve.json` and read/execute access to every parent directory in the path.

## Ingestion Errors

- **Parsing Failures**: If the `error.message` field appears in Kibana, it often indicates that the EVE JSON structure has been customized in a way that deviates from the standard format. Ensure `filetype: regular` is used and avoid manual modifications to the JSON structure in `suricata.yaml`.
- **Schema Mismatches**: Using highly experimental Suricata features or non-standard protocols may result in fields that do not map to the Elastic Common Schema (ECS). Check for fields in the `labels` or `unmapped` categories if expected data is missing from standard fields.
- **Log Rotation Issues**: If logs stop appearing suddenly, ensure that Suricata and the Elastic Agent are handling log rotation correctly. The Agent should detect when the file is moved and start reading the new file automatically.
